## 2. Project Overview

The system is a Hospital Queue Management and Appointment Coordination System.

Its purpose is to reduce unnecessary waiting, improve coordination between hospital receptionists and doctors, and allow patients to understand the status of their appointments and estimated waiting times.

The system connects three primary user groups:

1. Patients.
2. Hospital receptionists.
3. Doctors.

The hospital staff must have a dedicated desktop application installed on their computers. This is a core requirement, not an optional feature.

The backend will be built with Python and Flask, exposing a REST API that coordinates appointments, users, queue operations, doctor availability, and waiting-time calculations.

Patients will interact with an online, mobile-friendly interface. Doctors will have an authenticated interface that works well on a phone or computer.

All applications must communicate with the same central backend. The database must not be accessed directly by desktop clients.

The system must support multiple hospitals in its architecture, even if the initial deployment is for one hospital.

Patient interface → Flask API → PostgreSQL

Doctor interface → Flask API → PostgreSQL

The desktop application must never be trusted to decide independently whether a user is authorized to approve an appointment or modify a queue.

## 6. Appointment Workflow

Implement an explicit appointment state machine.

Suggested appointment states:

- Pending approval.
- Approved.
- Rejected.
- Reschedule requested.
- Rescheduled.
- Cancelled.
- Checked in.
- Completed.
- No-show.

Refine these states where necessary so they represent distinct business events rather than overlapping concepts.

A patient submitting an appointment request must not automatically be considered an approved appointment.

The receptionist must review the request before approval.

The backend must validate that:

- The selected doctor belongs to the selected hospital or department.
- The requested time is available.
- The patient is authorized to make the request.
- The appointment does not conflict with applicable scheduling rules.
- Repeated submissions do not accidentally create duplicate appointments.
- Only valid state transitions are accepted.
- Every approval, rejection, rescheduling, and cancellation is auditable.

Use transactions or appropriate database constraints to prevent double-booking under concurrent requests.

## 7. Queue Management Engine

The queue management engine is the central business feature.

Build it as a backend service with explicit rules and automated tests.

Support queues organized by hospital, department, doctor, and service where appropriate.

Distinguish between an appointment schedule and a live waiting queue. A patient may have an approved appointment without having checked in or entered the active queue.

A patient becomes eligible for the live queue according to the hospital's check-in policy.

Support:

- Appointment-based patients.
- Walk-in patients.
- Check-in timestamps.
- Queue entry timestamps.
- Queue positions.
- Patients waiting to be called.
- Patients who have been called.
- Patients whose consultations are in progress.
- Completed consultations.
- Cancelled appointments.
- Patients who miss their turn.
- Authorized queue priority.
- Temporary pauses.
- Doctor unavailability.
- Manual corrections with reasons.

Use explicit and documented queue rules. Do not rely on arbitrary sorting or fragile frontend logic.

Where priority is supported, make it configurable and auditable. Emergency triage must remain governed by qualified hospital personnel and established clinical protocols. The software must not independently make clinical triage decisions.

Prevent race conditions when multiple receptionists or doctors update the same queue concurrently.

Use database transactions, locking or another justified concurrency-control approach where necessary.

Generate stable queue-entry identifiers. Do not rely on a patient's visible queue number as a permanent database identifier.

Define what happens when a patient is skipped, returns after missing a call, cancels, or changes doctors.

Every important queue transition must produce a timestamped event.

## 8. Waiting-Time Estimation

Implement a dedicated waiting-time estimation service.

Do not pretend to know the exact time a patient will be seen.

Use available information such as:

- Number of eligible patients ahead in the queue.
- Historical consultation durations for the relevant doctor or service.
- Current consultation status.
- Doctor availability.
- Breaks and planned interruptions.
- Patients who have been called or are already being attended to.
- Relevant appointment scheduling rules.

Start with a simple, explainable model. Use historical median consultation duration when sufficient reliable data is available, with a documented fallback estimate when it is not.

The initial model may estimate the remaining time using the expected duration of consultations ahead, adjusted for current queue and doctor state.

If historical data is insufficient, show that the estimate is provisional rather than presenting false precision.

Display a range, such as "Estimated waiting time: 30–45 minutes," where uncertainty justifies it.

Recalculate the estimate when meaningful queue events occur.

Explain the assumptions and limitations of the estimator in the documentation.

Measure actual prediction error during testing or pilot deployment before making claims about accuracy.

Do not add machine learning unless a meaningful dataset and demonstrated need justify it.

## 9. GPS and Doctor Availability

Location tracking is a supporting feature, not the source of truth for queue management.

Design an optional doctor arrival-verification feature.

Potential signals include:

- The doctor's explicit check-in action.
- The doctor's declared availability.
- An optional location check initiated with permission.
- A timestamp of the last confirmed status.
- Receptionist confirmation when appropriate.

For an initial version, prioritize explicit check-in and availability updates.

If GPS is implemented, obtain permission, minimize the location data collected, explain its purpose, and avoid continuous background tracking unless it is demonstrably necessary, lawful, and explicitly authorized.

Do not store a detailed movement history merely to calculate queue estimates.

Use a configurable hospital geofence only if it is appropriate and technically supported. Explain location accuracy limitations and avoid treating GPS proximity as proof that a doctor is ready to consult.

Patients should see meaningful availability statuses such as:

- Expected.
- Checked in.
- Available for consultations.
- Consultation in progress.
- Temporarily unavailable.
- On break.
- Unavailable.

Only show statuses that can be supported by actual system events.

Do not expose a doctor's precise coordinates to patients.
